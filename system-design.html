What happens between "send" and the first word of the reply

Follow one message through the machinery that runs a large language model in production: from your app, through the traffic layers, onto the GPUs, and back as a stream of words. Every stop has a plain-English explanation and a technical one.

Request path: getting your message to the right machine

1

Your app opens one connection and keeps it open

When you press send, your app makes a single call to the AI provider and then waits on that open line. The reply doesn't arrive as one block. Words are pushed down the line the moment they're written, which is why answers appear to type themselves.

Under the hood

  • An HTTPS POST with stream: true. The server answers with Server-Sent Events: one small event per token or token group, then a final event with usage counts.
  • Everything is asynchronous. The client never blocks a thread per request, and neither does the server.
  • Two numbers define how fast it feels: time to first token (TTFT), which is mostly prompt processing, and time per output token (TPOT), the streaming speed after that.
  • Work that isn't interactive goes to a separate batch API: submit a file of requests, poll for results later, and pay less because the provider can run it in idle capacity.
2

The gateway checks who you are and how much you're allowed

Think of a front desk. It confirms your identity, checks you haven't used up your allowance, and turns away floods of traffic so one heavy user can't slow everyone else down. Nothing about AI happens here yet.

Under the hood

  • An ordinary, stateless web tier, scaled horizontally behind load balancers: TLS termination, API-key auth, and request validation.
  • Rate limits are counted in requests per minute and tokens per minute, because one 200K-token prompt costs as much as hundreds of short ones.
  • It stamps each request with a tenant identity and priority tier. Later layers use these for fair queuing and for keeping each customer's cached data separate (stop 12).
3

A smart router picks the GPU server that already remembers you

A provider runs hundreds of identical copies of the model. A naive dispatcher would deal requests out like cards. A smart one notices that a particular server has just handled the earlier part of your conversation and still has those notes in memory, so it sends you there and skips redoing that work. It also avoids servers that are already overloaded.

Under the hood

  • Chain hashing. The prompt is cut into fixed-size token blocks. Each block's hash includes the previous block's hash, so a block only counts as a match if everything before it matches too.
  • A fleet-wide index. In the precise version, engines such as vLLM, SGLang and TensorRT-LLM publish an event every time their cache changes. The router keeps a map from block hash to the servers holding it.
  • Scoring. Each candidate gets prefix match − load penalty, where load is KV-cache fullness and queue length. Matching on cache alone would pile everyone sharing a popular system prompt onto one server.
  • Measured results. One deployment reported 3× output throughput and 2× faster TTFT versus round-robin (Llama 3.1 70B).
  • The router also holds a central queue, giving one place for fairness, priorities and a "true demand" signal that drives autoscaling (stop 10).

Inside the GPU: how one server turns text into tokens

4

Your request joins a moving batch of thousands of others

A GPU is like a bus that's expensive to run whether it's full or empty, so servers never process one request at a time. The old approach waited until every passenger reached their destination before letting anyone new on. Modern servers let people board at every stop: the moment one reply finishes, a new request takes its seat.

Under the hood

  • Continuous batching (also called iteration-level scheduling or in-flight batching, from the Orca paper). The batch is rebuilt at every decode step, not once per batch.
  • Each step, the scheduler keeps running sequences, admits waiting ones only if enough free KV-cache blocks exist, and preempts low-priority sequences when memory runs out.
  • In vLLM this lives in a separate engine core process that owns the scheduler and the KV-cache manager. One or more API-server processes feed it over ZMQ sockets, and it drives one worker process per GPU.

5

The KV cache: the model's notes, and the scarcest thing on the chip

While reading your conversation, the model writes compact notes about every word so it never has to re-read them. These notes grow with every word, and they must sit in the GPU's fast memory next to the model itself. How many conversations a GPU can handle at once comes down to how many sets of notes fit. Servers store them in small labelled pages, like a well-organised filing cabinet, so no space is wasted.

Under the hood

  • Size per token = 2 (keys and values) × layers × KV heads × head dimension × bytes. For Llama 3.1 70B that's 2 × 80 × 8 × 128 × 2 bytes ≈ 320 KB per token.
  • So a single 128K-token request needs about 42 GB of cache, while the 70B model's weights alone are about 140 GB.
  • PagedAttention stores the cache in fixed-size pages scattered through memory, the way an operating system pages RAM. Each request has a block table pointing at its pages. This removes most of the waste from reserving maximum-length space up front.
  • Identical prompt prefixes can point to the same pages, which is how prompt caching works.
  • Storing the cache in FP8 instead of 16-bit roughly halves it, which doubles the batch. Cold pages can also be offloaded to CPU RAM or SSD.
6

Two very different jobs: reading your message, then writing the reply

Reading (prefill) takes in your whole message at once and keeps the chip's maths units fully busy. It decides how long you wait before the first word. Writing (decode) produces one word at a time, and each word requires sweeping through the entire model in memory. It decides how fast the words stream. Mixing both jobs on the same chip means a big incoming document can briefly stall everyone else's stream.

Under the hood

  • Prefill is compute-bound: all prompt tokens go through in parallel matrix multiplies. It sets TTFT.
  • Decode is memory-bandwidth-bound: each step reads all weights plus the growing KV cache to emit one token per sequence. It sets TPOT. Batching is what makes decode affordable, because one weight read serves the whole batch.
  • Interference: a long prefill entering a shared batch delays every decoding sequence.
  • Chunked prefill cuts long prompts into slices and interleaves them with decode steps, trading a little prefill efficiency for a bounded stall. The bigger fix is running the two phases on separate machines (stop 9).
7

One model, split across several GPUs that talk constantly

Large models don't fit on one chip. They're sliced so that every GPU holds a piece of every layer. All the GPUs work on the same batch at the same time and compare notes after each layer over an ultra-fast cable inside the server. Together, that group of GPUs is one "copy" of the model, called a replica.

Under the hood

  • Tensor parallelism (TP): each weight matrix is split across GPUs, with an all-reduce after every layer. That synchronisation is so frequent it needs NVLink, so TP usually stays within one 8-GPU node.
  • Pipeline parallelism (PP): different layers go on different nodes. It's tolerant of slower links, but you have to keep the pipeline full.
  • Expert parallelism (EP): in mixture-of-experts models, the experts are spread across many GPUs and tokens are routed to whichever GPU holds their expert. DeepSeek uses this at very large scale.
  • Data parallelism (DP): whole replicas are copied. This is how a service scales out.
8

Two speed tricks that don't change the answer much, or at all

Smaller numbers: storing the model's values with fewer digits (quantisation) halves its memory footprint with very little quality loss, so more fits per chip. Guess and check: a small, fast helper model drafts the next few words, and the big model checks all of them in one go. Correct guesses are kept, and the first wrong one is replaced by the big model's own choice, so the final text is exactly what the big model would have written.

Under the hood

  • Quantisation: FP8 or INT8 weights (about 1 byte per parameter) and INT4 methods such as GPTQ and AWQ (about 0.5 bytes). This frees memory for KV cache and speeds up the memory-bound decode.
  • Speculative decoding: a draft model proposes K tokens and the target model verifies all K in one forward pass. A rejection-sampling rule keeps the output distribution identical to the target model's, so it's lossless.
  • Typical speed-ups are 2–3× and depend on the acceptance rate: predictable text such as code or structured output speeds up more than open-ended prose. Variants like EAGLE and Medusa replace the separate draft model with light extra heads on the main model, and vLLM supports several forms.

Scaling: from one server to a fleet

9

Separate teams for reading and writing

Because reading and writing are such different jobs (stop 6), the largest operators now give each its own pool of machines. One team reads your message and writes up the notes. It hands those notes to a second team, which does the writing. A huge document arriving no longer freezes anyone's stream, and each team can be sized for its own workload.

Under the hood

  • Prefill–decode disaggregation. The DistServe research system reported serving up to 4.48× more requests, or meeting 10.2× tighter latency targets, versus co-located serving. Microsoft's Splitwise made the same case on production-like traces.
  • The cost is moving the KV cache from prefill to decode GPUs over InfiniBand or RDMA. It's only worth it when that transfer is cheap relative to the interference it removes.
  • It's now standard in frontier stacks: DeepSeek runs separate prefill and decode node groups, NVIDIA Dynamo ships it, and vLLM supports it, including shared KV pools across machines.
10

Add machines when the queue grows, lend them out at night

Demand swings through the day. The system watches how many requests are waiting, not just how busy the chips look, and adds or removes model copies to match. Starting a new copy is slow because hundreds of gigabytes of model have to be loaded first, so operators scale ahead of demand and keep spare copies warm.

Under the hood

  • GPU utilisation is a poor scaling signal, because a memory-bound decode can look "busy" at any load. Better signals are queue depth, KV-cache usage and SLO attainment (TTFT and TPOT percentiles). llm-d's central queue exposes a "true demand" metric for exactly this purpose.
  • Cold start covers provisioning the node, pulling the container, and loading weights into GPU memory. That's minutes for large models, so the levers are predictive scaling, warm pools, fast weight streaming and, for small models, scale-to-zero.
  • Prefill and decode pools scale independently once disaggregated.
  • Off-peak capacity gets reused: DeepSeek shifts inference nodes to research and training during low-load night hours.

How many GPUs does one model need?

There are three different answers. The minimum to load one copy depends only on the model's size. A production copy needs extra room for many conversations' notes. The whole service is that copy multiplied by however many copies the traffic needs. Try the calculator: it shows memory per copy, not total fleet size.

Sharing and cost: many customers, one set of chips

12

Thousands of strangers share the same GPU safely

Your conversation runs on the same chip, in the same batch, through the same copy of the model as many other people's. That's safe because the model itself is read-only, and each conversation's notes sit in their own labelled pages that only that conversation can read. The pages are freed when you're done. The one subtle risk is timing: if notes were shared between customers, someone could notice that certain text is processed suspiciously fast and guess it was recently seen. Providers prevent this by keeping each customer's reusable notes separate.

Under the hood

  • Isolation is logical, not physical. Weights are shared and read-only. Each sequence has its own block table, and attention kernels only read that sequence's pages.
  • Contention is handled with gateway quotas, priority tiers, fair queuing at the router, and preemption order in the scheduler.
  • Prefix-cache side channel. Cache hits are measurably faster than misses, so shared caches across trust boundaries can leak prompt contents. The mitigation is a per-tenant cache_salt (supported in vLLM, and in NVIDIA Dynamo's routing), so reuse happens only within one tenant. Research systems such as CacheSolidarity isolate selectively to keep more reuse. A salt is an isolation key, not authentication: the gateway must set it from a verified identity.
  • Per-customer fine-tunes are served as LoRA adapters on one shared base model. Each request in a batch applies its own adapter (S-LoRA and Punica techniques).
  • Hardware partitioning (MIG slices, MPS, dedicated replicas, confidential-computing GPUs) is reserved for small models, dedicated enterprise capacity or regulated workloads.
13

Why you pay per token, and how providers make tokens cheaper

GPUs are rented by the hour whether they're busy or not. Your bill is per word because the provider's real cost is the price of an hour of GPU divided by how many words that hour produced. Every trick on this page (batching, caching, routing, splitting pools, quantising) exists to squeeze more words out of each GPU-hour. That's why re-sent conversation history is often billed cheaply as a "cache hit": the provider genuinely didn't have to recompute it.

Cost per million tokens

– per million output tokens

Raw compute cost only. It excludes prefill work, networking, staff, idle reserve and margin.

Under the hood

  • Formula: cost per 1M tokens = hourly GPU price ÷ (tokens/sec × 3,600 × utilisation) × 1,000,000.
  • The levers: batch size (limited by KV memory), cache hit rate, quantisation, speculative decoding, disaggregation, and keeping utilisation high across the day.
  • Real numbers: at an assumed $2 per H800-hour, DeepSeek put its daily inference cost at about $87,072. It reported up to 9,213 prefill tokens per second per GPU, helped by a 56.3% cache hit rate.

Glossary

Token
A chunk of text, roughly three-quarters of an English word. Models read and write in tokens.
Prefill
Reading the whole prompt in one pass. Sets the wait before the first word.
Decode
Writing the reply one token at a time. Sets streaming speed.
KV cache
The model's stored notes about tokens already read, kept in GPU memory.
TTFT / TPOT
Time to first token / time per output token: the two latency numbers that matter.
Replica
One complete running copy of the model, often spread over several GPUs.
Node
One physical server, typically holding 8 GPUs.
NVLink / InfiniBand
Fast links between GPUs inside a server / between servers.
Mixture of experts (MoE)
A model where each token uses only a few of many sub-networks ("experts").
LoRA
A small add-on that customises a shared base model without copying it.
